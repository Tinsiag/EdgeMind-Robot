1About This Guide 
1.1 Purpose 
This manual describes the interface and use of FloorPlanner and the 
syntax definition of physical constraint for FPGA products in order to help 
you add physical constraints to your design. As the software is subject to 
change without notice, some information may not remain relevant and may 
need to be adjusted according to the software that is in use. 
All physical constraints have higher priority than the global Place & 
Route settings in Gowin Software. The global Place & Route settings can 
be configured via clicking "Project > Configuration > Place & Route" from 
the menu bar in Gowin Software.

2Physical Constraints Syntax Definition 
2.1 Syntax Rules 
 Each constraint statement must end with an English semicolon. 
 The constraint object obj_name must be enclosed in English double 
quotation marks. 
 In a constraint statement, multiple constraint locations (obj_location) can be 
specified, separated by English commas. For example, multiple IO locations 
can be written as "A11,B2". 
 Each part of the constraint statement must be separated by a space. 
2.2 I/O Location Constraints 
The IO constraints can be used to constrain ports to the specified IO 
locations. The specific IO locations can be found in the device's Pinout 
manuals. 
2.2.1 Syntax 
IO_LOC "obj_name" obj_location [exclusive]; 
Note! 
For shorted I/O pins within the package, only manual constraint editing is supported; 
automatic constraint generation and editing by FloorPlanner are not supported. 
The definitions of shorted I/O pins can be found in the Pin Definitions > 
User I/O Pins > [pin]_[End][Row/Column Number][A/B] of the Pinout 
manuals. 
Example 
PAGE 15
2 Physical Constraints Syntax Definition 2.2 I/O Location Constraints 
 
SUG1541-1.0E 5(84) 
 
IO_LOC "port0" D9_L8A; 
// In the GW1N-2 B-version WLCSP100H package, IOL6B and IOL8A 
are shorted. IOL6B corresponds to D9, while IOL8A corresponds to 
D9_L8A. The D9_L8A location supports manual editing only, and the object 
port0 is constrained to the D9_L8A location. 
2.2.2 Parameter Description 
Table 2-1 I/O Location Constraint Parameter Description 
Parameter Description 
obj_name Specifies the name of the port for which the location constraint is 
to be applied.  
obj_location Specifies the location where the port can be placed. 
exclusive Optional keyword. If specified, the resource at obj_location is 
exclusively reserved for obj_name, and no other object can be 
placed at this location. 
2.2.3 Example 
Example 1 
IO_LOC "port0" G2; 
// The object port0 is constrained to location G2 in the GW5AT-15 
B-version MBGA132 package. 
Example 2 
IO_LOC "port1" P10,N10,G2; 
// The object port1 is constrained to locations P10, N10, and G2 in the 
GW5AT-15 B-version MBGA132 package. During placement, the first valid 
location among the three specified locations is selected. 
Example 3 
IO_LOC "port2" P10,N10,G2 exclusive; 
// In the GW5AT-15 B-version MBGA132 package, the object port2 is 
constrained to locations P10, N10, and G2, and these three locations can 
only be occupied by port2.

2.3 I/O Attribute Constraints 
I/O attribute constraints are used to set various I/O attribute values, 
such as the I/O standard (IO_TYPE), pull-up/pull-down mode 
(PULL_MODE), and drive strength (DRIVE) of a port. For detailed attribute 
setting specifications, refer to the data sheet of the corresponding device. 
Multiple attributes can be specified in a single constraint statement. Each 
attribute can be separated by spaces. 
2.3.1 Syntax 
IO_PORT "obj_name" attribute = attribute_value; 
2.3.2 Parameter Description 
Table 2-2 I/O Attribute Constraint Parameter Description 
Parameter Description 
obj_name Specifies the name of the port for which the attribute 
constraint is to be applied. 
attribute Specifies the attribute name. 
attribute_value Specifies the attribute value. 
 
Specifies the attributes and attribute values of the port for which I/O 
attribute constraints are to be applied. For the specific attributes and 
attribute values that can be constrained, refer to the Gowin Programmable 
I/O (GPIO) User Guide for the corresponding device. 
2.3.3 Example 
Example 1 
IO_PORT "port_1" IO_TYPE = LVTTL33; 
// Sets the IO_TYPE attribute of port_1 to LVTTL33. 
Example 2 
IO_PORT "port_2" IO_TYPE = LVTTL33 PULL_MODE = KEEPER; 
// Sets the IO_TYPE attribute of port_2 to LVTTL33 and the 
PULL_MODE attribute to KEEPER.

2.4  Primitive Location Constraints 
Primitive Constraints are used to constrain the primitives to the 
specified locations. Primitive Constraints can be used to constrain 
primitives such as LUT, MUX, DFF, DL, SSRAM, PLL, BSRAM, DSP, 
DSPLite, IOLOGIC, DQS, DDRDLL, MIPI_DPHY_RX, MIPI_DPHY_TX, 
and SCRAMBLE. 
2.4.1 Syntax 
INS_LOC "obj_name" obj_location [exclusive]; 
2.4.2 Parameter Description 
Table 2-3 Primitive Location Constraint Parameter Description 
Parameter Description 
obj_name Specifies the primitive instance name for which the location 
constraint is to be applied. 
obj_location Specifies the location where the primitive can be placed. The 
format varies depending on the primitive type. For details, refer to 
the location format description for each primitive type in the 
following sections. 
exclusive Optional keyword. If specified, the resource at obj_location is 
exclusively reserved for obj_name, and no other object can be 
placed at this location. 
2.4.3 Location Formats 
CFU Location Formats 
The primitive types included in a CFU are LUT, MUX, DFF, DL, and 
SSRAM. The following location formats are supported for location 
constraints. 
Table 2-4 Single Location  
Location Formats Description 
RxCy[0-3][A-B] Specifies the location of a single 
LUT/MUX/DFF/DL. 
RxCy Specifies the location of a single SSRAM.

Example 1 
INS_LOC "lut_1" R5C10[0][A];

INS_LOC "ins_2" R5C6[2] exclusive;

INS_LOC "ins_3" R[2:6]C2;

INS_LOC "ins_4" R[2:4]C[2:6] exclusive; 
// ins_4 is constrained to a location within the region spanning rows 2 
to 4 and columns 2 to 6, and this region can only be occupied by this 
constrained object. 
Example 5 
INS_LOC "ins_5" R[2:4]C[2:6][1];   
// ins_5 is constrained to the second CLS at any GRID location within 
the region spanning rows 2 to 4 and columns 2 to 6. 
PLL Location Formats 
PLL location constraints support specifying a PLL by direction. The 
location format is PLL_<Direction>, where <Direction> indicates the 
direction and can be one of the following: 
 L: Left  
 R: Right  
 T: Top  
 B: Bottom  
When multiple PLLs are available in the same direction, a specific PLL 
can be specified using the format PLL_<Direction>[n], where n is the PLL 
location index. For example: PLL_L[0], PLL_R[1], PLL_T[0], and PLL_B[2]. 
PAGE 20
2 Physical Constraints Syntax Definition 2.4 Primitive Location Constraints 
 
SUG1541-1.0E 10(84) 
 
Example 
INS_LOC "pll_name" PLL_L[0]; 
// In the GW5AST-138 B-version PBGA484A package, this constraint 
assigns pll_name to the first PLL location on the left side. 
BSRAM Location Formats 
BSRAM location constraints support specifying locations by GRID row 
number. Depending on whether ECC is supported, BSRAM locations can 
be divided into regular BSRAM locations and ECC BSRAM locations. Each 
ECC BSRAM location corresponds to two consecutive regular BSRAM 
resource locations. 
1. Regular BSRAM locations and ECC-capable BSRAM locations 
The location format is BSRAM_R<x>[n], where: 
 x indicates the GRID row number where the BSRAM is located. 
 n indicates the BSRAM location index within the corresponding 
GRID row. 
Example 1 
INS_LOC "bsram_name" BSRAM_R10[2]; 
// In the GW5AST-138 B-version PBGA484A package, the third 
BSRAM location in row 10 is a regular BSRAM location. This constraint

2.5 Group Constraint 
Group Constraints include Primitive Group Constraints and Relative 
Group Constraints, as described below. 
2.5.1 Primitive Group Constraints  
Primitive Group Constraints are used to define a group constraint. A 
group is a collection of various types of instance objects. Primitive Group 
Constraints allow instances such as LUT, DFF, DL, IOLOGIC, Buffer, 
BSRAM, SSRAM, DSP , PLL, DDRDLL, DQS, and DSPLite to be added to 
a group. By constraining the location of the group, the locations of all 
objects in the group can be constrained accordingly. Primitive Group 
Constraints also support the use of the wildcards ? and *. The ? wildcard 
matches a single character, while the * wildcard matches zero or more 
characters.  
Syntax 
Primitive Group Definition: 
GROUP group_name = {"obj_names" } [exclusive]; 
GRP_LOC group_name group_location [exclusive]; 
Note! 
The Primitive Group Constraint syntax consists of two statements: the group definition 
statement and the group location statement. Both statements are required; if either 
statement is missing, the constraint is considered invalid. 
Parameter Description

obj_names Specifies the names of the primitive instances to be included in 
the group constraint. 
group_location Specifies the locations where the group constraint can be placed.

2.11.6 MODE Net Constraints 
The MODE function pins include MODE0, MODE1, and MODE2. 
These functions can be implemented either through dedicated I/O 
configuration or through dedicated configuration controlled by the internal 
FPGA logic. These two implementation methods are mutually exclusive, 
and the same implementation method must be selected for all of these 
function pins; that is, either dedicated I/O configuration or dedicated 
configuration controlled by the internal FPGA logic must be selected for all 
of them. 
When the MODE functions are controlled by the internal FPGA logic, 
the MODE_LD signal is added in addition to MODE0, MODE1, and 
MODE2. MODE_LD is a load signal. On the rising edge of MODE_LD, the 
values of MODE0 to MODE2 controlled by the internal logic are loaded. 
That is, the values of MODE0 to MODE2 are updated on each rising edge 
of MODE_LD. Before the first rising edge of MODE_LD, the values of 
MODE0 to MODE2 configured during bitstream download are used. When 
the MODE functions are controlled by the internal FPGA logic, MODE net 
physical constraints must be added. For details on MODE usage, refer to 
the FPGA Product Programming and Configuration Guide for the 
corresponding device.  
Note! 
Only Arora V and Arora III devices support MODE Net Constraints.

3.1 Introduction 
FloorPlanner is a physical constraint editor and designed in-house by 
Gowin. It supports reading and editing the attributes and locations of I/O, 
Primitive, and Group, etc. It also supports the generation of place 
constraints files according to your configuration. These files define I/O 
attributes, as well as locations of primitives and modules. FloorPlanner 
provides easy and fast placement and constraint editing functions to 
improve the efficiency of writing physical constraint files. 
The functions of Gowin FloorPlanner are as follows: 
 Supports importing user design files and constraint files, editing 
constraint files, and exporting constraint files. 
 Supports displaying I/O Port, Primitive, Group constraint information, 
and other constraint information in user design files. 
 Supports creating, editing, and modifying constraint information. 
 Supports grid mode, macro cell mode and primitive mode of chip array. 
 Supports displaying the Package View based on package information. 
 Supports synchronized display of the Chip Array and Package View. 
 Supports real-time display and differences display of constraints 
locations. 
 Supports setting location information by dragging. 
 Supports configuring I/O port attributes, including batch configuration. 
 Supports displaying and editing Clock Net Constraints. 
 Supports constraints validity checking.
